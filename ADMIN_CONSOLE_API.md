# Admin Console Integration Spec (Backend + OCPP)

This document is the **integration specification** for wiring an external **Admin Console / Operator Portal** to:

1) the **Megawatt backend API** (REST + Socket.IO), and
2) the **Megawatt OCPP CSMS** (charger WebSocket + admin HTTP API).

Source of truth in this repo:

- OCPP server: `backend/src/services/OCPPServer.ts` (WebSocket + admin HTTP)
- Backend API server: `backend/src/index.ts`
- Backend CPO routes: `backend/src/routes/cpo.ts`
- Backend internal bridge: `backend/src/routes/internal.ts`

---

## 2) Identity + routing rules

### 2.1 `chargePointId` routing key (charger ↔ CSMS)

The OCPP server routes chargers strictly by the **URL path**:

```text
ws://35.224.174.50:9000/ocpp/<chargePointId>
```

Implementation:

- `chargePointId` is extracted via regex `/\/ocpp\/(.+)$/`.
- The CSMS stores the connection in memory:
  - `connections: Map<chargePointId, WebSocket>`

### 2.2 Database mapping

Your Admin Console (and backend) should treat the charger’s identity as:

- `charging_points.ocpp_id == chargePointId`

All status/session updates from OCPP are applied using that key.

## 3) OCPP 1.6J wire protocol (JSON over WebSocket)

### 3.1 Frame formats

**CALL** (request):

```json
[2, "<uniqueId>", "<action>", {"...payload"}]
```

**CALLRESULT** (response):

```json
[3, "<uniqueId>", {"...payload"}]
```

**CALLERROR** (error):

```json
[4, "<uniqueId>", "<errorCode>", "<errorDescription>", {"...errorDetails"}]
```

### 3.2 Correlation

- `uniqueId` is generated by the sender.
- For CSMS → charger admin commands, the CSMS waits for a matching CALLRESULT/CALLERROR with the same `uniqueId`.

## 4) OCPP charger → CSMS actions (implemented)

These are actions currently handled by `OCPPServer`.

### 4.1 BootNotification

Charger CALL:

```json
[2,"<id>","BootNotification",{
  "chargePointVendor":"string",
  "chargePointModel":"string",
  "chargePointSerialNumber":"string?",
  "firmwareVersion":"string?",
  "meterSerialNumber":"string?",
  "meterType":"string?",
  "iccid":"string?",
  "imsi":"string?"
}]
```

CSMS behavior:

- Best-effort DB write:
  - `charging_points.status = 'AVAILABLE'`
  - `charging_points.last_status_update = NOW()`
- Always responds `Accepted` (even if DB down)

CSMS CALLRESULT:

```json
[3,"<id>",{"status":"Accepted","currentTime":"<ISO>","interval":30}]
```

### 4.2 Authorize

Charger CALL:

```json
[2,"<id>","Authorize",{"idTag":"string"}]
```

CSMS behavior:

- Accept logic controlled by env:
  - `OCPP_ACCEPT_ALL_ID_TAGS` (default `true`)
  - `OCPP_ALLOWED_ID_TAGS` (comma-separated)

CSMS CALLRESULT:

```json
[3,"<id>",{"idTagInfo":{"status":"Accepted|Invalid"}}]
```

### 4.3 StatusNotification

Charger CALL:

```json
[2,"<id>","StatusNotification",{
  "connectorId":1,
  "status":"Available|Preparing|Charging|SuspendedEVSE|SuspendedEV|Finishing|Reserved|Unavailable|Faulted",
  "errorCode":"string?",
  "timestamp":"<ISO>?"
}]
```

CSMS behavior:

- Status mapping → DB:
  - Available/Preparing → `AVAILABLE`
  - Charging/Suspended*/Finishing → `OCCUPIED`
  - Reserved → `RESERVED`
  - Unavailable/Faulted → `OUT_OF_SERVICE`

DB updates:

- `charging_points.status = <mapped>`
- `charging_points.last_status_update = NOW()`

If the status becomes fault/offline mid-session:

- CSMS calls backend internal alert:
  - `POST /api/internal/cpo/alert`

CSMS CALLRESULT:

```json
[3,"<id>",{}]
```

### 4.4 Heartbeat

Charger CALL:

```json
[2,"<id>","Heartbeat",{}]
```

CSMS behavior:

- Best-effort: `charging_points.last_status_update = NOW()`

CSMS CALLRESULT:

```json
[3,"<id>",{"currentTime":"<ISO>"}]
```

### 4.5 StartTransaction

Charger CALL:

```json
[2,"<id>","StartTransaction",{
  "connectorId":1,
  "idTag":"string",
  "meterStart":0,
  "timestamp":"<ISO>"
}]
```

CSMS behavior:

- Generates `transactionId` (number)
- Finds `charging_points` by `ocpp_id = chargePointId`
- Links to latest backend session where `charging_sessions.status='ACTIVE'`
- Persists:
  - `charging_sessions.ocpp_transaction_id = transactionId`

CSMS CALLRESULT:

```json
[3,"<id>",{"transactionId":12345,"idTagInfo":{"status":"Accepted"}}]
```

### 4.6 MeterValues

Charger CALL (minimum fields we consume):

```json
[2,"<id>","MeterValues",{
  "transactionId":12345,
  "meterValue":[{
    "timestamp":"<ISO>",
    "sampledValue":[{
      "measurand":"Energy.Active.Import.Register",
      "unit":"Wh|kWh",
      "value":"12345"
    }]
  }]
}]
```

CSMS behavior:

- Extracts energy from `Energy.Active.Import.Register`.
- Tracks deltas using an in-memory per-chargepoint map.
- Updates DB totals:
  - `charging_sessions.energy_delivered += deltaKwh`
  - `charging_sessions.total_cost += deltaKwh * pricePerKwh`

Then forwards progress to backend internal API:

- `POST /api/internal/session/progress`

CSMS CALLRESULT:

```json
[3,"<id>",{}]
```

### 4.7 StopTransaction

Charger CALL:

```json
[2,"<id>","StopTransaction",{
  "transactionId":12345,
  "meterStop":23456,
  "timestamp":"<ISO>",
  "reason":"Local|Remote|..."
}]
```

CSMS behavior:

- Finds latest ACTIVE session for that chargepoint and marks it `COMPLETED`.

CSMS CALLRESULT:

```json
[3,"<id>",{"idTagInfo":{"status":"Accepted"}}]
```

### 4.8 FirmwareStatusNotification

Charger CALL:

```json
[2,"<id>","FirmwareStatusNotification",{
  "status":"Downloaded|DownloadFailed|Downloading|Idle|InstallationFailed|Installing|Installed"
}]
```

CSMS behavior:

- Logs status
- Best-effort: bumps `charging_points.last_status_update = NOW()`

CSMS CALLRESULT:

```json
[3,"<id>",{}]
```

## 5) OCPP CSMS → charger commands (admin-triggered)

These are exposed via the **OCPP server admin HTTP API** and send corresponding OCPP CALL frames.

### 5.1 ChangeAvailability

OCPP CALL:

```json
[2,"<id>","ChangeAvailability",{"connectorId":0,"type":"Operative|Inoperative"}]
```

Expected CALLRESULT:

```json
[3,"<id>",{"status":"Accepted|Rejected|Scheduled"}]
```

### 5.2 UnlockConnector

OCPP CALL:

```json
[2,"<id>","UnlockConnector",{"connectorId":1}]
```

Expected CALLRESULT:

```json
[3,"<id>",{"status":"Accepted|Rejected"}]
```

### 5.3 GetConfiguration

OCPP CALL:

```json
[2,"<id>","GetConfiguration",{"key":["SomeKey"]}]
```

Expected CALLRESULT (charger-defined shape):

```json
[3,"<id>",{"configurationKey":[{"key":"SomeKey","readonly":false,"value":"..."}]}]
```

### 6.4 POST `/admin/unlock-connector`

Body:


Body:

### 6.6 Forwarding / webhook configuration (OCPP → backend)

The OCPP server can forward:

- **session progress** to the backend internal endpoint, and
- **CPO alerts** to the backend internal endpoint.

This is configured using:

- environment variables (recommended for production), OR
- the admin endpoints below (runtime configuration).

#### GET `/admin/forwarding`

Response:

```json
{
  "progressTargetUrl": "http://<backend-host>:3000/api/internal/session/progress",
  "alertTargetUrl": "http://<backend-host>:3000/api/internal/cpo/alert",
  "internalTokenSet": true
}
```

#### POST `/admin/forwarding`

Body (any field optional; only provided fields are updated):

```json
{
  "progressTargetUrl": "https://api.example.com/api/internal/session/progress",
  "alertTargetUrl": "https://api.example.com/api/internal/cpo/alert",
  "internalToken": "<shared-secret>"
}
```

Response:

```json
{
  "ok": true,
  "progressTargetUrl": "...",
  "alertTargetUrl": "...",
  "internalTokenSet": true
}
```

## 7) Backend internal “forwarded” payloads (OCPP → backend)

These are the payloads that the OCPP server forwards into the backend so the Admin Console can get realtime data.

> The integration requirement is: **OCPP server must know the backend internal URL and token.**

### 7.0 OCPP server forwarding env vars

The OCPP server supports these env vars:

- `SESSION_PROGRESS_WEBHOOK_URL` (defaults to `http://localhost:3000/api/internal/session/progress`)
- `CPO_ALERT_WEBHOOK_URL` (defaults to `http://localhost:3000/api/internal/cpo/alert`)
- `INTERNAL_TOKEN` (sent as header `x-internal-token`)

> Backward compatibility: if `SESSION_PROGRESS_WEBHOOK_URL` / `CPO_ALERT_WEBHOOK_URL` are not set, the server will fall back to `INTERNAL_URL` (older config) and then to localhost defaults.

### 7.0.1 INTERNAL_TOKEN (must match backend)

The OCPP server forwards to backend internal endpoints using:

```http
x-internal-token: <INTERNAL_TOKEN>
```

So your backend deployment must set the same value:

```bash
INTERNAL_TOKEN=<same-token-as-ocpp>
```

Current generated token on OCPP (Phase A):

```text
lDm7mSrr-1I4QM-1HKeqjwPqh6LPdGSFMdlSjw64v98
```

When your backend is deployed publicly, update the OCPP targets (Phase B):

```bash
curl -X POST http://35.224.174.50:9000/admin/forwarding \
  -H 'Content-Type: application/json' \
  -d '{
    "progressTargetUrl":"https://<backend-domain>/api/internal/session/progress",
    "alertTargetUrl":"https://<backend-domain>/api/internal/cpo/alert"
  }'
```

### 7.1 POST `/api/internal/session/progress`

Auth header:

```http
X-Internal-Token: <INTERNAL_TOKEN>
```

Body:

```json
{
  "sessionId": "<uuid>",
  "energyDelivered": 1.234,
  "totalCost": 24.68,
  "powerKw": 7.2
}
```

Socket.IO emit results:

- room: `session:<sessionId>`
  - event: `session_progress`
- room: `cpo`
  - event: `session_progress`

### 7.2 POST `/api/internal/cpo/alert`

Auth header:

```http
X-Internal-Token: <INTERNAL_TOKEN>
```

Body (example: charger fault mid-session):

```json
{
  "type": "charger_fault_mid_session",
  "ocppId": "yc0117126010020",
  "chargerStatus": "OUT_OF_SERVICE",
  "sessionId": "<uuid>",
  "userId": "<uuid>",
  "chargingPointId": "<uuid>",
  "stationId": "<uuid>",
  "stationName": "<string>",
  "pointNumber": "<string>"
}
```

Socket.IO emit results:

- room: `cpo`
  - event: `cpo_alert`
